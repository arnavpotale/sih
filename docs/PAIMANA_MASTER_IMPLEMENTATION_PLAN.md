# PAIMANA MASTER IMPLEMENTATION PLAN

## 1. Executive Summary
PAIMANA AI is transitioning from a descriptive "infrastructure reporting dashboard" to a predictive and prescriptive "infrastructure intelligence and early-warning platform." This plan outlines the technical roadmap to replace heuristic mockups with authentic machine learning (XGBoost/SHAP) and a decision-support workflow for MoSPI/IPMD officials. The focus is exclusively on identifying, explaining, and intervening in high-risk projects.

## 2. Current Architecture
- **Frontend**: React, Vite (Single Page Application)
- **Backend**: FastAPI (Python), SQLAlchemy ORM, Pydantic
- **Database**: PostgreSQL (currently running SQLite temporarily), seeded with 20 sample projects.
- **AI Logic**: Currently residing in client-side heuristics (`src/utils/aiEngine.js`).

## 3. Current Feature Inventory
- Executive Overview (KPIs, Charts)
- AI Early Warning Radar
- National GIS Map
- Projects Registry (Successfully migrated to FastAPI backend)
- Benchmarking & Drivers
- North East Focus
- CUF & What-If Sandbox
- Drishti AI Assistant
- Project Detail / X-Ray Modal

## 4. Current Strengths
- Beautiful, sovereign-grade MoSPI design language.
- Excellent map and geospatial representation.
- Solid component-based React architecture.
- Functional FastAPI backend foundation is already established.

## 5. Current Weaknesses
- **Information Overload**: The UI is extremely data-heavy, showing numbers rather than driving decisions.
- **Fake AI**: Predictions, SHAP values, and risk scores are hardcoded heuristics rather than trained ML models.
- **Data Limitation**: Only cross-sectional snapshots exist; genuine time-series early-warning models cannot be validated without longitudinal data.

## 6. SIH Requirement Mapping
| SIH PS Requirement | PAIMANA Implementation |
| :--- | :--- |
| Cost/Time Overrun Prediction | ML Pipeline (XGBoost) predicting risk probabilities. |
| Early Warning System | Background anomaly detection & Alert engine. |
| Benchmarking | Backend API comparing peers by sector/budget. |
| CUF vs External Variable Assess | Controlled ML experiments (Model A vs B vs C). |
| Prescriptive Intelligence | Intervention workflow & SHAP factor explanation. |

## 7. Gap Analysis
- **Missing ML Pipeline**: No actual trained models.
- **Missing Anomaly Detection**: No Isolation Forest implementation.
- **Missing Workflow**: No way for an official to "assign an intervention" to a project manager and track resolution.
- **Missing Data Strategy**: No longitudinal dataset to prove "early warning" lead time.

## 8. Target Product Vision
**From Dashboard to Decision-Support Platform.**
The system will monitor the data in the background, surface anomalies, explain *why* they happened, recommend interventions, and track those interventions to completion.

## 9. User Personas
1. **MoSPI / IPMD Official (Primary)**: Needs to know what's broken and what to do about it.
2. **Project Manager / Implementing Agency**: Needs to provide updates, submit evidence, and respond to interventions.

## 10. User Journeys
- **The Officer Flow**: Log in -> Command Centre -> See Top 3 Critical Alerts -> Open Project X-Ray -> View SHAP explanation -> Assign "Review Land Clearances" intervention to Agency.
- **The Agency Flow**: Receive Intervention Alert -> Upload Clearance Certificate -> Update Physical Progress -> Mark Resolved.

## 11. Information Architecture
1. **COMMAND CENTRE**: (Landing Page) Focus on Alerts & Priority Projects.
2. **PROJECTS**: Registry, X-Ray, Updates.
3. **INTELLIGENCE**: Early Warning Radar, GIS, Benchmarking.
4. **SIMULATION**: CUF What-If.
5. **AI**: Drishti Assistant.

## 12. Feature Hierarchy
- **P0 (Must Have)**: FastAPI integration, XGBoost Risk Models, SHAP Explanations, Command Centre.
- **P1 (High Value)**: Anomaly Detection (Isolation Forest), Intervention Workflow, Peer Benchmarking.
- **P2 (Useful)**: CUF What-If Simulator (Python backed), GIS Map Backend integration.
- **P3 (Future/Cut)**: Complex Chat LLM (Drishti), Custom bidding marketplaces.

## 13. Backend Architecture
React UI -> FastAPI (Routers: `/projects`, `/alerts`, `/ml`, `/interventions`) -> SQLAlchemy -> PostgreSQL.
Models run via `scikit-learn`/`xgboost` loading `.pkl` artifacts on server start.

## 14. Database Architecture (Minimal Schema)
- `projects` (Baseline static details)
- `project_updates` (Longitudinal snapshots of progress/expenditure)
- `alerts` (Generated by ML/Anomaly engines)
- `interventions` (Assigned tasks related to alerts)

## 15. ML Architecture
- **Baseline**: Logistic Regression.
- **Primary Model**: XGBoost (for non-linear infrastructure relationships).
- **Explainability**: SHAP (TreeExplainer).
- **Unsupervised**: Isolation Forest (Anomalies).

## 16. Data Strategy
Because real historical data is missing, we will generate a **Reproducible Synthetic Longitudinal Dataset** (simulating 48 months of progress for our 20 baseline projects) to prove that our ML models *would* catch delays 6 months early. This data will be strictly labelled as synthetic for demonstration purposes.

## 17. AI/LLM Architecture (Drishti)
Drishti will be integrated last. It will use a structured Tool-Calling agent (e.g., Langchain + OpenAI/Gemini) with strict access to APIs (e.g., `get_project_risk(id)`) so it NEVER hallucinates financial numbers.

## 18. Alert Architecture
A backend cron job (or simulated stream) evaluates projects daily against the ML models. If probability > threshold, an Alert record is created (Severity: High/Medium, Trigger: Cost Overrun).

## 19. Intervention Workflow
Alert -> Official creates Intervention -> Assigned to Agency -> Agency submits Status="Resolved" -> Official approves.

## 20. UI Transformation Plan
- **Remove**: Generic KPI counters that do not drive action.
- **Add**: An "Action Required" Inbox on the home screen.
- **Modify**: Project Detail Modal becomes "Project X-Ray" focused entirely on Risk Factors (SHAP) and Benchmarks.

## 21. External Repository Evaluation
- **Syncfusion Controls**: Excellent reference for EVM (Earned Value Management) math, but too heavy to import. *Recommendation: Extract EVM formulas, discard repo.*
- **Airport Construction Risk (ML)**: Good reference for XGBoost hyperparameter tuning on construction datasets. *Recommendation: Reference methodology, write custom pipeline.*
- **Task/Project Management**: *Recommendation: Build a simple CRUD `interventions` table ourselves rather than inheriting massive Jira-clone repos.*

## 26. Technical Risks
- ML endpoints slowing down FastAPI. *Mitigation: Load model into memory on startup.*
- Pydantic schema mismatches with frontend expectations.

## 27. Data Risks
- Judges might penalize the use of synthetic data. *Mitigation: Be highly transparent. The models are real, the pipeline is real. The synthetic data is purely to demonstrate "Early Warning Lead Time" which is impossible to demonstrate with a single snapshot.*

## 28. Implementation Risks
- Wasting time on complex LLM integrations that hallucinate. *Mitigation: Do not build Drishti until the deterministic APIs are rock solid.*

## 29. What Should NOT Be Built
- Do NOT build an external contractor bidding/auction platform.
- Do NOT build complex HR/Resource management tracking.
- Do NOT build 3D CAD / BIM viewers (out of scope).

## 30. Definition of Done
- All fake heuristics removed from `aiEngine.js`.
- XGBoost and Isolation Forest running in Python.
- Frontend rendering actual API data.
- Intervention workflow functional.
- Zero hallucinated ML metrics.

## 31. Recommended Implementation Sequence
1. Synthetic Time-Series Data Generator.
2. Python ML Training Pipeline.
3. FastAPI Endpoints (Risk, SHAP, Anomalies).
4. Alert & Intervention Database schema.
5. Command Centre UI Overhaul.
6. Delete `aiEngine.js`.
